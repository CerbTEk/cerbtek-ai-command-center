## Result

- Company managers connect their Microsoft 365 or Google account through CerbTek-owned server configuration. Customer client IDs, tenant IDs and secrets are removed from onboarding.
- One own-mailbox connection per provider per company. Read, send or both are explicit capability choices. Reconnect invalidates old bindings immediately; disconnect clears Kairo's credential bytes and blocks future use. Provider-wide consent revocation remains a separate action.
- OAuth completion requires two independent browser proofs, current original actor/company authority, one-time state and verified provider identity/grants. Tokens remain unusable until finalization. Return stays at the existing canonical `https://www.cerbtek.com/app/kairo` route.
- Managers select a Microsoft folder or Gmail label, preview a bounded batch, and explicitly import an inquiry into an assigned workflow. Email content remains untrusted data, not an instruction or sender-authentication credential.
- Gmail and Microsoft share the exact accepted-draft, designated reviewer, independent approval, current authority, durable single-dispatch and audit controls. Gmail MIME encodes exactly the approved recipient, subject and body. A provider acknowledgement means acceptance, not delivery. Ambiguous/failed transport after dispatch never permits an automatic resend.
- Installed workflows pin one connection. A second connected provider does not silently change the sending account. New binding key is `email_connection_id`; legacy immutable `microsoft_connection_id` records continue to work. Existing RPC names remain compatibility aliases where documented.

## Remaining limitations and prerequisites

- Provider registration/verification and credential configuration were not performed or asserted by this release. Server configured flags validate setting shape, not actual working grants or app verification.
- Microsoft defaults to organizational work/school accounts. Personal Outlook and shared/delegated mailboxes are unsupported. Google uses the signed-in account's own mailbox; no shared-mailbox impersonation or service accounts.
- Gmail label selection limits Kairo intake. `gmail.readonly` still grants mailbox-wide read scope. External production Google verification and, where applicable, independent restricted-scope security assessment remain external dependencies. Google testing-mode refresh-token restrictions must be reviewed before pilot use.
- Intake is manual, bounded and conservative. Complex/ambiguous addresses, unsupported MIME/charset or over-limit messages can be skipped with a visible count. Attachments are never downloaded. There is no automatic polling, sync, attachment reasoning or in-thread reply guarantee.
- Existing independent AI activation/budget controls remain in place. This candidate neither activates paid inference nor sends messages by itself.
- Browser/pixel QA, real OAuth, enterprise policy and provider delivery remain untested. Production verification confirmed all 36 changed SQL bodies, service-only RPC ACLs, private-table RLS and denied browser grants, all 13 Edge bundles, canonical-origin preflights, unauthorized rejection and safe callback error returns. Security advisors report no warnings/errors; the private table adds one expected RLS-without-browser-policy informational finding.
